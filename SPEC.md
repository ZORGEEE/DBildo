# DBildo — функциональная спецификация первой версии

Дата: 2026-09-30. Статус: проект требований, без реализации.
Основа: [ARCHITECTURE.md](ARCHITECTURE.md).
Целевые интеграции: PostgreSQL, ClickHouse, Airflow, официальный DeepSeek Harness.
Формат: desktop с общим UI для будущей веб-версии. Инфраструктура, DAG и окружения
создаются с нуля в текущем проекте; готовых подключений и CI/CD нет.

## Что пользователь сможет сделать

Подключить обе базы и Airflow, открыть DAG, перейти от задачи к SQL и таблицам,
исследовать результаты и поручить агенту диагностику. Агент получает те же
объекты и средства выполнения, что и пользователь. Исправления видны как diff,
а повторный запуск имеет отдельный отслеживаемый результат.

## Экран IDE

Первая поставка — Electron-приложение с локальным backend. Общий React UI
не зависит от Electron; desktop-функции вынесены в небольшой адаптер платформы.
Открытие workspace использует системный диалог, а операции над файлами идут
через backend. Закрытие приложения завершает его backend/runtime; Docker-стенд
имеет отдельный жизненный цикл и не останавливается без явного действия.

```text
┌ Проект / окружение ───────── Поиск объектов ───────── Статус подключений ┐
│ Каталог         │ SQL / Python / DAG / Lineage       │ Агент           │
│                 │                                    │                 │
│ PostgreSQL      │ Редактор либо интерактивный граф    │ Диалог          │
│ ClickHouse      │                                    │ Инструменты     │
│ Airflow         │                                    │ Контекст        │
│ Файлы проекта   ├────────────────────────────────────┤ Изменения       │
│                 │ Данные / График / Схема / Логи      │                 │
│                 │ Результат и состояние операции     │ Ввод поручения  │
└─────────────────┴────────────────────────────────────┴─────────────────┘
```

Панели изменяют размер и скрываются. Вкладки, размеры и выбранные объекты
восстанавливаются при открытии workspace. Контекстное действие «Обсудить с агентом»
прикладывает ссылку на объект и его снимок. Вложения можно проверить и удалить.

## Каталог и запросы

- Подключения создаются раздельно для dev/prod и показывают окружение постоянно.
- Проверка соединения отличает недоступность сети, ошибку авторизации и права.
- Каталог загружается порционно; поиск работает по именам и описаниям.
- Открытие таблицы показывает схему, ключи, метаданные и время их получения.
- SQL-вкладка привязана к connection/database/schema; диалект всегда виден.
- Выполняется выделение или явно выбранный statement. Произвольные многооператорные
  SQL-скрипты и сквозные транзакции редактора откладываются до отдельного этапа.
- Результат имеет query ID, схему, длительность, состояние и признак усечения.
- Большие результаты не загружаются целиком в DOM или память агента.
- Фильтрация и сортировка явно различают локальную выборку и новый запрос к БД.
- Для одного запроса поддерживаются отмена, ошибка и частичный результат.
- Int64/Decimal передаются без потери точности; NULL, время и timezone сохраняют
  явную семантику. Экспорт не меняет типы незаметно.

Табличные результаты и профиль колонки — разные представления. Профили показывают
число NULL, число различных значений и распределение, если операция поддерживается.
Выборочные/приближённые оценки отмечаются. Графики первой версии: линия по времени,
столбцы по категории и распределение числовой колонки. Пользователь выбирает
оси и агрегат; у графика сохраняются запрос и ссылка на исходный результат.

Начальные настраиваемые ограничения для MVP: 200 строк preview, 100 строк в одном
ответе инструмента агенту, не более 32 KiB на этот ответ, 30 секунд для интерактивного
запроса. Превышение выдаёт ссылку на результат и способ чтения следующей части.
Это проектные значения, их нужно проверить на реальных задачах.

## DAG и происхождение данных

Представление DAG показывает задачи Airflow, связи, TaskGroup, состояния и длительность.
Статус принадлежит конкретному run и попытке. Для mapped tasks учитывается map_index;
их нельзя объединять в одну задачу без возможности раскрытия.

Нажатие на задачу открывает её код (если подключён репозиторий), параметры,
входы/выходы и логи конкретной попытки. История позволяет сравнить два запуска
и перейти к проблемной задаче. При потере подключения отображается последнее
известное состояние и время обновления.

Представление lineage показывает движение данных между PostgreSQL, задачами и
ClickHouse. Фильтры: выбранный объект, N уровней upstream/downstream, окружение,
подтверждённость связи. Группировка по базе, схеме и пайплайну позволяет исследовать
большой граф по частям. Масштабирование, поиск, minimap и центрирование на выборе
обязательны. Автоматическое расположение не должно сбрасывать выбор пользователя.

Первая версия визуализирует DAG из workspace и опубликованные в dev Airflow,
включая создаваемый вместе со стендом пример. Drag-and-drop редактирование
произвольного Python DAG с гарантированным обратным преобразованием не входит
в MVP. Код меняется в редакторе или через diff агента, после чего граф обновляется.

## Агент и доступ к контексту

Harness запускается через официальный SDK; отдельный адаптер скрывает preview API
от бизнес-логики IDE. Плагин данных вызывает общий domain service. Прямой доступ
браузера к SDK и секретам подключений отсутствует.

Каждая сессия связана с workspace и окружением. Начальное сообщение получает
обзор каталога, текущие вложения и сведения о доступных инструментах. Полный текст
файлов, данные и логи извлекаются по мере исследования. Объекты содержат source,
observed_at, version и доступные ссылки. Недоступные данные не заменяются догадками.

Логи и строки БД считаются данными: найденные внутри них инструкции не меняют
политику исполнения. Разрешения действуют на backend и в источнике, независимо
от ответа модели. В проектных настройках отдельно задаются возможности чтения,
редактирования файлов, изменения данных и управления запусками. Полный контекст
можно дать без автоматического разрешения всех этих операций.

Секреты хранит credential provider ОС/сервера. В каталог попадают только ссылки
на них. Shell агента не получает административные credentials в обход адаптеров.
Для облачной модели настройки подключения явно определяют, какие выборки можно
передавать провайдеру. Собственный endpoint остаётся альтернативой развёртывания.

UI показывает сообщения, состояния, вызовы инструментов и их результаты.
Сессия сохраняется; пользователь может отменить ход агента. Отмена инициирует
остановку дочерних операций и отражает их фактический итог, включая незавершённую
серверную отмену. Восстановление сессии не повторяет уже выполненные изменения.

## Контракты backend

Это проект API IDE, а не существующие методы SDK Harness.

| Группа | Операции |
| --- | --- |
| connections | list, create, test, update, remove |
| catalog | search, describe, refresh, lineage |
| queries | start, status, page, cancel, export |
| pipelines | list, graph, runs, taskAttempts, logs, trigger, clear |
| sessions | create, send, attachContext, events, cancel, resume |
| changes | propose, diff, validate, apply |

Длительная операция возвращает operation_id. Команды идут через HTTP; прогресс —
через SSE с event_id для восстановления. Пагинация результатов и логов использует
cursor. Общие поля ошибок: code, message, retryable, operation_id и безопасные details.

Доменные события IDE: query.started/page/completed/failed/cancelled,
catalog.updated, run.updated, agent.message/tool/status, change.proposed/validated.
На границе Harness его события преобразуются в эти типы. Имена здесь не являются
утверждением о названиях событий официального runtime.

Запуск DAG и другие изменения имеют request_id. Backend хранит статус команды
до отправки и сверяет результат перед повтором. Если исход неизвестен, UI показывает
это состояние: автоматический повтор не должен создавать дубликат запуска.

Обновления каталога выполняются независимо по подключениям. Отказ одной базы
не блокирует редактор, Airflow и доступные источники. При запуске приложения
восстанавливаются сессии и сверяются незавершённые операции.

## Проверки и применение изменений

ChangeSet содержит файлы, исходные hashes, diff, окружение и результаты проверок.
Конфликт с внешним изменением не затирает файл. Применение сохраняет запись
об исходной версии, чтобы обратное изменение было просматриваемым.

SQL сначала проходит синтаксическую проверку и планирование там, где это доступно.
EXPLAIN ANALYZE не считается пассивной проверкой — он выполняет запрос.
Python проверяется в окружении, соответствующем Airflow. Импорт DAG может выполнять
пользовательский код, поэтому проверка не идёт в процессе сервера IDE.

В MVP применяется локальный diff, затем отдельное действие публикует проверенный
снимок в каталог dev Airflow. История публикаций хранит revision/hash и результат
разбора DAG. Незавершённые правки workspace не попадают в выполняемый DAG.
Кнопка повторного запуска работает с опубликованной версией и показывает её.
Если соответствие версий подтвердить нельзя, IDE явно сообщает об этом.

## Создание dev-окружения

Compose-стенд включает PostgreSQL для исходных данных, ClickHouse, отдельную
metadata DB PostgreSQL и компоненты Airflow 3 с LocalExecutor. Каждый сервис
имеет health check; инициализация выполняется до проверки подключений из IDE.
Точные версии образов/providers фиксируются после интеграционной проверки.

Первый workspace содержит `dags/`, `sql/` и `tests/`. Пример orders создаёт
воспроизводимый путь PostgreSQL → Airflow → ClickHouse и проверки результата.
Сначала предоставляется работающий пример; несовместимость схемы включается
отдельным тестовым сценарием для диагностики агентом.

Запуск/остановка стенда, состояние Docker и ошибки инициализации описываются
в инструкции проекта. IDE должна работать и с удалёнными источниками без Docker.
Повторный запуск стенда сохраняет данные; очистка volumes — отдельное явное действие.
В первой версии настраивается dev; конфигурация prod не создаётся.

Веб-совместимость проверяется браузерным запуском того же UI против того же API:
каталог, SQL, DAG, результаты и агент работают без Electron. Для отдельного
серверного продукта позже добавляются вход, серверные workspace, TLS и изоляция;
доступ к локальным файлам пользователя через браузер не предполагается.

## Этапы и критерии приёмки

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| 0. Основа и стенд | Desktop-каркас, самостоятельный backend, Compose и закреплённые версии SDK/runtime | Стенд проходит health checks; SDK вызывает инструмент; общий UI открывается в desktop и браузере |
| 1. Рабочее место | Каталог обеих БД, SQL, результаты и графики | Запросы обеих БД работают; большие результаты, типы, ошибки и отмена проверены |
| 2. Airflow | DAG, TaskGroup, запуски, mapped tasks, попытки и логи | UI совпадает с API выбранного Airflow; сбой/повтор задачи отображается корректно |
| 3. Общий контекст | Lineage, связи задач и таблиц, инструменты агента | Из узла DAG можно перейти к таблицам; агент исследует те же объекты и ссылается на результаты |
| 4. Исправления | ChangeSet, проверки, применение и наблюдение повторного запуска | Агент диагностирует тестовую поломку; diff проверяется; конфликт не затирает файл |

Сквозной тестовый сценарий: тестовый DAG переносит orders из PostgreSQL в ClickHouse;
целевая схема намеренно не соответствует исходной. IDE показывает ошибку, агент
читает лог и схемы, предлагает изменение и показывает проверяемые свидетельства.
После исправления в dev и доставки DAG повторный запуск проходит согласованные
проверки строк/типов за один data interval. Зелёный статус DAG сам по себе
не подтверждает корректность данных.

Дополнительные приёмочные случаи: истёкший токен Airflow, недоступная база,
обрыв потока результата, превышение лимита, отмена долгого запроса, устаревшая схема,
динамический DAG с неполным lineage и перезапуск IDE во время операции.
Также проверяются закрытие Electron без оставшихся процессов runtime, повторное
открытие workspace, сохранение данных после перезапуска Compose и ошибка разбора
публикуемого DAG. Отсутствие Docker не блокирует работу с удалёнными подключениями.

## За пределами первой версии

Совместное редактирование, собственный оркестратор, универсальная генерация DAG
мышью, автоматический production deploy, полный column-level lineage произвольного
Python и полноценная совместимость с расширениями VS Code. Эти возможности
потребуют отдельных решений после проверки сквозного сценария.
